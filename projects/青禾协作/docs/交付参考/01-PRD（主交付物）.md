## 1. 要解决的问题

一支约十人的软件团队有一张任务表，记录每件事由谁负责、何时交付、做到哪一步。客户要求、进度和安排变化发生在聊天里，没有写回任务表。接手的人只能翻聊天，才能知道当前安排。

成功时，维护人打开任务表就能看见已经确认的安排，不用从聊天里重推一遍。

## 2. 使用者和场景

使用者是这张任务表的维护人。做题的人自己扮演这个角色。不用找真实负责人，信息不足时把缺的事实留下来。

聊天里的客户、客服、销售、项目负责人、开发，是记录来源，不是网页账号。

只有一条连续场景：

1. 载入初始工作清单和 A 批，分析、核对、确认、导出。
2. 用导出的任务表加上 B 批，再走一遍，再导出。
3. 把同一批、相同编号、相同正文再导入一次。结果不得多出一行，也不得破坏已经确认的字段。

## 3. 范围

### 3.1 要做

| 编号 | 需求 | 验收 |
|---|---|---|
| R1 | 上传一张任务表和一批聊天记录，并在页面上看见读入内容 | 字段、编号、正文与文件一致 |
| R2 | 使用者主动发起分析。程序真实调用外部对话模型，找出可能要更新的任务 | 页面能区分处理中、完成、失败 |
| R3 | 每条建议给出原值、建议值、依据原话。不确定处标成待核实，并写明缺什么 | 依据能指回聊天编号。不能只给结论 |
| R4 | 使用者对每条建议采纳、否决，或修改后采纳 | 未确认的建议不改任务表 |
| R5 | 导出完整新任务表，以及一份简短变更说明 | 导出的表能再次作为现有任务表载入 |
| R6 | 在已处理的任务表上导入下一批，重复 R1–R5 | 同一批再次导入不新增行动、不覆盖已确认结果 |

一条聊天可以对应零条、一条或多条建议。同一任务的不同字段分开建议。

每条建议至少有：任务编号（对不上现有任务时标明「不对应现有任务」）、字段名、原值、建议值或「不建议修改」、聊天编号和原话、不确定点、使用者决定。决定只有四种：待确认、采纳、否决、修改后采纳。只有采纳和修改后采纳写回该字段。

### 3.2 不做

- 登录、多人权限、按角色分账号
- 接入真实聊天软件，或自动收消息
- 复杂历史系统、公网部署
- 让业务使用者把答案从聊天工具抄进网页
- 把这三份附件的处理结论写死在程序里
- 程序代替使用者确认

网页要能读取字段相同、内容不同的新 CSV。

页面怎么排、怎样让人先看重要变化、模型在哪一步调用、导出文件的具体格式，留给 PRD。PRD 不能为了少一次点击而自动落表。

## 4. 数据

CSV 为 UTF-8，带 BOM。保留原始编号和正文含义。正式运行时上传 CSV。

任务表：编号、工作项、责任人、当前安排、截止日、验收条件。  
聊天记录：编号、时间、来源、内容。

初始表确认时点是 9 月 14 日 18:00。共 4 行：W-01 账单导出支持全部结果，W-02 邀请新成员前增加审批，W-03 旧共享链接关闭与核查，W-04 按项目查看费用。A 批 10 条，先处理。B 批 6 条，接在 A 批确认结果之后。字段原文见 CSV，不在这里改写。

跑完一次，留下三样东西：更新后的完整任务表、仍可核对的建议清单、变更说明。变更说明写清改了什么、依据是哪句原话、还缺什么。没改的行也要能说明保持原安排。

## 5. 业务规则

PRD 把下面每条写成可检查的验收条款。

1. 任务表表示当前已确认的安排。「开发中」「本期不做，保留待讨论」「待需求确认，未排开发」都是安排。它们表示事情还在，不表示任务已经完成。
2. 可以提议改表的，是项目负责人的决定，以及已经核对、并且对得上验收条件的事实。
3. 销售的承诺和催期、客户的希望、开发的自测进度，必须单独看得见。这些不能单独改写责任人、截止日或验收状态。
4. 同一事项按时间读。后出现的负责人决定，覆盖更早的请求。不能用整批最后一条聊天覆盖整张表。
5. 一条信息可以只改责任人或日期。同一行其余已确认字段保持不动。
6. 原有 4 项始终保留。某一批没提到的任务，原样留下。
7. 没有依据时不猜负责人、日期、故障原因或验收结果。输出「不建议修改」或「待核实」，并写明缺哪一项事实。
8. 客户把问题说清楚，不表示功能已经做好。开发说做完，不表示验收通过。
9. 使用者确认之前，任务表不变。
10. 同一批以相同编号、相同正文再次导入时，不新增任务，不新增重复行动，不引入新的业务事实，不覆盖已经确认的字段。

例子：表上是林川、9 月 18 日。项目负责人后来说改由周宁负责、9 月 19 日交付。网页分别建议改责任人和日期，并显示原话。确认后这两个字段才改。客户只说「希望提前」，日期不动。

## 7. 失败和边界

- 有诉求但没有准数时，不把诉求写成已确定安排。A-03、B-02 的上线希望不能变成 W-02 的截止日。
- 新旧说法冲突时，两条都要看得见。A-03 与 A-04、B-02 与 B-03 必须同时可见。
- 信息不足时保留未知。A-08 不能编出页面、现象、负责人或日期。
- B 批的输入是 A 批确认后的任务表。只有使用者没有采纳 A 批任何建议时，输入才仍是 9 月 14 日的初始表。
- 模型调用失败时，页面不显示分析成功。已经确认的任务表和已经作出的决定还在。配置恢复后可以重试。这次检查是模拟，不把额度打尽。

## 3. 功能需求

### 3.1 主流程

```
① 载入      上传任务表 CSV + 一批聊天记录 CSV，页面显示读入内容
   ↓
② 分析      使用者主动发起；真实调用外部对话模型；页面区分 处理中 / 完成 / 失败
   ↓
③ 核对      逐条查看建议：任务编号、字段、原值、建议值、依据原话、不确定点
   ↓
④ 确认      逐条决定：待确认 / 采纳 / 否决 / 修改后采纳
   ↓
⑤ 写回      只有「采纳」「修改后采纳」写入对应字段
   ↓
⑥ 导出      任务表 + 建议清单 + 变更说明
   ↓
⑦ 下一批    用导出的任务表 + 下一批聊天，回到 ①
   ↓
⑧ 重复导入  同一批相同编号相同正文再导入 → 不新增行、不覆盖已确认字段
```

**页面状态必须可区分**：处理中 / 完成 / 失败。未确认的建议不得改动任务表。

### 3.2 功能需求与验收

| 编号 | 需求 | 验收标准 |
|---|---|---|
| **FR1** 上传与查看 | 上传一张任务表和一批聊天记录，页面显示读入内容 | 页面显示的任务编号、字段、正文与上传文件一致；列缺失或格式错误时明确报错，不静默吞掉 |
| **FR2** 发起分析 | 使用者主动点击发起；程序**真实调用**外部对话模型，找出可能需要更新的任务 | 页面能区分处理中／完成／失败；失败时**不显示分析成功** |
| **FR3** 建议可核对 | 每条建议给出原值、建议值、依据原话；不确定处标「待核实」并写明缺什么 | 依据能指回聊天编号，展示原话；不能只给结论 |
| **FR4** 人工决定 | 对每条建议采纳、否决，或修改后采纳 | 未确认的建议不改任务表；决定只有四种 |
| **FR5** 导出 | 导出完整新任务表，以及一份简短变更说明 | 导出的表**能再次作为现有任务表载入** |
| **FR6** 继续更新 | 在已处理的任务表上导入下一批，重复 FR1–FR5 | 同一批再次导入：不新增行、不新增重复行动、不覆盖已确认字段 |

### 3.3 建议的数据结构（字段级）

一条聊天可以对应 **零条、一条或多条**建议。**同一任务的不同字段分开建议**，避免一句聊天改掉整行。

| 字段 | 说明 |
|---|---|
| 任务编号 | 对不上现有任务时，明确标「不对应现有任务」 |
| 字段名 | 工作项 / 责任人 / 当前安排 / 截止日 / 验收条件 |
| 原值 | 当前任务表里的值 |
| 建议值 | 新值，或「不建议修改」 |
| 依据 | 聊天编号 + 原话（可多条） |
| 不确定点 | 缺什么事实；无则空 |
| 使用者决定 | 见 3.4 |

### 3.4 四种决定

| 决定 | 是否写回该字段 |
|---|---|
| 待确认 | 否 |
| 采纳 | 是 |
| 否决 | 否 |
| 修改后采纳 | 是（用修改后的值） |

**只有「采纳」和「修改后采纳」写回该字段。** 程序不得代替使用者确认；不得为了少一次点击而自动落表。

### 3.5 数据字段与导出物

| 导出物 | 内容 | 可再用性 |
|---|---|---|
| 更新后的任务表 | 全部任务、全部 6 个字段，编号与正文含义保留 | 可再次作为「现有任务表」上传 |
| 建议清单 | 每条建议的全部字段 + 依据原话 + 使用者决定 | 仍可核对 |
| 变更说明 | 改了什么、依据哪句原话、还缺什么；**没改的行也要说明保持原安排** | 可对上每处改动 |

导出文件的具体格式（列集、编码、命名、是否独立成文件）由设计决定，但必须满足上表三项。

## 4. 业务规则与验收条款

原始需求第 5 节的十条规则，逐条落成可检查的验收条款。

| # | 规则 | 可检查的验收条款 |
|---|---|---|
| **R1** | 任务表表示当前已确认的安排；「开发中」「本期不做」「待需求确认」都是安排，不表示已完成 | 页面与导出物中，这些状态原样保留，不得被改写为「已完成」/「验收通过」 |
| **R2** | 可提议改表的依据只有两类：项目负责人的决定；已核对且对得上验收条件的事实 | 每条改变字段的建议，依据中必须含项目负责人决定，或已核对的事实；否则标「待核实」 |
| **R3** | 销售的承诺与催期、客户的希望、开发的自测进度必须单独可见，不能单独改写责任人／截止日／验收状态 | 仅由上述来源构成的建议，不得被接受为改写责任人、截止日、验收状态；且该原话仍要在依据中可见 |
| **R4** | 同一事项按时间读，后出现的负责人决定覆盖更早请求；不得用整批最后一条覆盖整张表 | 建议须指向具体任务与字段；不得出现「据此改写整行/整表」的建议 |
| **R5** | 一条信息可以只改责任人或日期，同一行其余已确认字段保持不动 | 采纳一条建议后，该行其余字段值在导出表中逐字不变 |
| **R6** | 原有 4 项始终保留；某一批没提到的任务原样留下 | 任意批次处理后，任务数不减；未被提及的任务所有字段值不变 |
| **R7** | 没有依据时不猜负责人、日期、故障原因或验收结果，输出「不建议修改」或「待核实」，并写明缺哪项事实 | 信息不足的建议必须带不确定点说明；不得出现无依据的具体值 |
| **R8** | 客户把问题说清楚，不表示功能已经做好；开发说做完，不表示验收通过 | 「开发自测通过」类原话不得使验收条件／验收状态变为通过 |
| **R9** | 使用者确认之前，任务表不变 | 未做决定或决定为「待确认」「否决」时，导出表对应字段值与原值一致 |
| **R10** | 同一批以相同编号、相同正文再次导入：不新增任务、不新增重复行动、不引入新事实、不覆盖已确认字段 | 重复导入后行数不变、建议不重复产生、已确认字段值不变 |

**示例（来自原始需求）**：表上是林川、9 月 18 日；项目负责人后来说改由周宁负责、9 月 19 日交付 → 网页**分别**建议改责任人和日期，并显示原话；确认后这两个字段才改。客户只说「希望提前」→ 日期不动。

## 5. 边界、失败处理与成功指标

### 5.1 不做清单（明确排除）

- 登录、多人权限、按角色分账号
- 接入真实聊天软件，或自动收消息
- 复杂历史系统、公网部署
- 让业务使用者把答案从聊天工具抄进网页
- 把这三份附件的处理结论**写死在程序里**
- **程序代替使用者确认**

### 5.2 红线

| 红线 | 说明 |
|---|---|
| 不预写答案 | 分析必须由模型对当前上传的数据真实推导，不得内置附件结论 |
| 不用纯规则替代分析 | 规则只约束模型输出，不代替模型判断 |
| 不粘贴他处答案 | 不得把别处生成的答案粘进网页冒充自动流程 |
| 不自动落表 | 不得为减少点击而跳过人工确认 |
| 不展示密钥 | 页面不展示密钥；服务地址、模型名、密钥由运行配置注入 |

### 5.3 失败与异常处理

| 情形 | 必须的行为 |
|---|---|
| **模型调用失败** | 页面不显示分析成功，进入失败状态；**已确认的任务表和已作出的决定还在**；配置恢复后可重试 |
| **信息不足** | 保留未知，标「待核实」并写明缺什么；不得编造页面、现象、负责人或日期 |
| **新旧说法冲突** | 两条都要看得见。例如 A-03 与 A-04、B-02 与 B-03 必须同时可见，并说明哪条被放下 |
| **部分字段更新** | 只改到的字段变化，同一行其余已确认内容还在 |
| **诉求无准数** | 有诉求但没有准数时，不把诉求写成已确定安排（A-03、B-02 的上线希望不能变成 W-02 的截止日） |
| **重复导入** | 不新增行、不新增重复行动、不覆盖已确认字段 |
| **B 批输入错位** | B 批的输入必须是 A 批确认后的任务表；只有使用者未采纳 A 批任何建议时，输入才仍是 9 月 14 日初始表 |
| **超过可接受时延** | 单批分析超过 3 分钟→ 视为失败状态，不写回、不导出；已确认数据保留，可重试 |
| **模型调用次数超限** | 单批超过 3 次模型调用→ 停止并进入失败状态，不得静默重试绕过上限 |

### 5.4 验收样例基线

> 以下用作检查产品与提示词的**样例**，不代替模型分析（模型必须自行推导出等价结果）。
> 本节已包含原始需求第 8 节 5 处拍板结果（2026-10-25 定案）。

**A 批之后**

- **W-01 四个字段不改**：A-02 说明金额差异源于只导出第一页、页面扣费无错；A-10 客户接受；A-09 仍由林川负责、9 月 18 日交付，另需客服提供跨页核对样本（样本是依赖，不改字段）。
- **W-02 四个字段不改**：A-04 决定本期不插入；A-03 作为被放下的销售请求留在依据里。
- **W-04 四个字段不改**：A-05（客户丙＝交付项目）与 A-06（客户丁＝部门/成本中心）口径冲突，本批无负责人决定。
- **W-03 的责任人、截止日、验收条件不改**：A-07 只证明已知链接已关闭、复测打不开，历史同类链接尚未核完。
- **A-08「页面不顺」不新增任务**：保留一条待核实建议，缺页面与具体现象。

**B 批之后**（建立在 A 批字段不变的前提下）

| 任务 | 字段 | 结果 | 依据 |
|---|---|---|---|
| W-01 | 责任人 | 林川 → **周宁** | B-01 |
| W-01 | 截止日 | 9 月 18 日 → **9 月 19 日** | B-01 |
| W-01 | 验收条件 | **不改**（原句保留） | B-01「验收条件不变」 |
| W-01 | 当前安排 | **全部导出已完成并自测通过，待客服用客户样本核对跨页总额** | B-05（开发说做完 ≠ 验收通过） |
| W-02 | 当前安排 | **本期不做；材料已收到；请销售纠正 18 日承诺；排期另议** | B-03 是决定 |

### 5.5 成功指标（可度量）

| 指标 | 定义 | 目标值（已定稿） |
|---|---|---|
| **产物齐全率** | 每次导出都产出 任务表 + 建议清单 + 变更说明 | **100%** |
| **建议可核对率** | 含聊天编号与原话引用的建议数 ÷ 建议总数 | **100%** |
| **重复导入幂等率** | 重复导入后新增行数为 0 的批次占比 | **100%** |
| **已确认字段保护率** | 重复导入后已确认字段未变更数 ÷ 已确认字段总数 | **100%** |
| **模型调用失败率** | 分析失败次数 ÷ 分析总次数 | 不设上限（受外部服务影响）；但失败时 **100% 进入失败状态**且不写回、不导出 |
| **单批分析时延** | 一次分析从发起到返回的耗时 | **≤ 3 分钟** |
| **单批模型调用次数** | 一批聊天分析消耗的模型调用次数 | **≤ 3 次** |

> 以上目标值为验收基线（定稿于 2026-10-25）。任何一项不达标即不得交付。

### 6.2 已定稿（2026-10-25，产品与验收参数 6 项）

1. **成功指标目标值**：产物齐全率 / 建议可核对率 / 重复导入幂等率 / 已确认字段保护率 均为 **100%**；模型调用失败率不设上限，但失败时必须 100% 进入失败状态且不写回、不导出。详见 5.5。
2. **单次分析可接受时延**：**≤ 3 分钟**；超时视为失败状态，可重试。
3. **导出文件格式（定稿）**：三份独立文件，不合并——
   - `任务表.csv`：UTF-8 带 BOM，6 列（编号、工作项、责任人、当前安排、截止日、验收条件），列序固定，可再次上传。
   - `建议清单.json`：每条建议的全部字段、依据原话与使用者决定。
   - `变更说明.md`：改了什么、依据哪句原话、还缺什么；未改行说明保持原安排。
4. **数据访问边界**：程序**只读写自己产物目录内的文件**，不读工作目录以外的路径，不读密钥以外的配置。
5. **模型调用额度上限**：单批分析 **≤ 3 次模型调用**；超限停止并进入失败状态，不得静默重试绕过。
6. **是否引入后台任务**：**不引入**。分析采用**同步执行 + 页面「处理中」状态**；使用者可在分析完成后继续操作，失败可重试。

> **实现选型不写进本 PRD**（原始需求第 9 节要求）：编程语言、框架、模型服务商、配置注入方式属实现选择，不作为产品验收基线。
> 产品层面已固定的集成约束：分析由**外部对话模型**完成；服务地址、模型名、密钥由**运行配置注入**；页面**不展示密钥**；失败时进入失败状态。
